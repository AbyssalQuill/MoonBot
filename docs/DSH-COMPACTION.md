# 桌面端 DSH 的最优上下文压缩（永久会话）

本文回答一个问题：**DSH 桌面端在永久会话下，压缩阈值取多少最省钱。**
结论是 **0.16**（160,000 token），稳健区间 **14%~18%**。复算脚本：`docs/dsh-compaction-math.mjs`。

> 姊妹篇：`docs/COMPACTION-MATH.md` 是 MoonBot（服务端、内置 DSH）的那一套。
> 两篇用的是**同一个模型**，但参数各自按自己的实测数据标定 —— 结果撞在同一个点上（0.16），互为交叉验证。

---

## 0. 一句话结论

> **上下文本体几乎不花钱；花钱的是"整段重读"。**
> 所以阈值要取在"少压"和"别让每次重读太贵"之间 —— 桌面端的答案是 **0.16**。

这与直觉相反。桌面端原本的缺省是 **0.8**（`compaction-basic` 的出厂值），而 `dsh-web-app` 那一层
更是把自动压缩**整个关掉了**（实测会话上下文一路涨到 74.8 万 token）。按本文的模型，
0.8 → 0.16 相当于 **每天省 51%**。

---

## 1. 为什么是"重读"在花钱

DeepSeek 官方单价（空闲时段，元/百万 token，来源 <https://api-docs.deepseek.com/zh-cn/quick_start/pricing/>）：

| 项 | 价格 | 相对 |
|---|---|---|
| 输入 · 缓存命中 | **0.02** | 1× |
| 输入 · 缓存未命中 | **1** | **50×** |
| 输出 | **4** | 200× |

**命中与未命中差 50 倍** —— 这是整个成本结构的支点。缓存命中与未命中是两种完全不同的商品。

桌面端实测（`~/.dsh/storages/session_projcache/sessions/*.json`，10 个会话）：

```
累计 cacheRead   2,481,099,008 tok
累计 未命中         30,300,018 tok
累计 输出            4,021,151 tok
```

**98.8% 的输入是缓存读。** 也就是说：把上下文从 40 万带到 80 万，每步只多花
`0.02 元/M × 40 万 = ¥0.008`；但压缩之后那一次**整段重读**，是按 1 元/M 计价的。

---

## 2. 成本模型

```
每次请求成本 = a₀ + b·C                 C = 本次请求的上下文
每天成本     = steps·(a₀ + b·(R+T)/2) + (steps·g/(T−R))·重建成本
```

| 符号 | 含义 | 桌面端取值 |
|---|---|---|
| `b` | 每 token 每步的承载成本 | **= 缓存读价 = 0.02 元/M**（实测斜率就是它） |
| `a₀` | 每步固定开销 | ¥0.002 |
| `W` | 模型窗口 | 1,000,000 |
| `g` | 每步上下文增长 | **≈ 5,500 tok**（本机实测 `(未命中+输出) ÷ 步数`） |
| `R` | 压缩后落点 | `retainRatio × W` |
| `T` | 压缩阈值 | `thresholdRatio × W` |
| `s` | 摘要体量 | ≈ 3,000 tok |
| 重建成本 | `pMiss·R + pOut·s` | ¥0.032（当 R=20,000） |

对 `T` 求导令零：

```
(T − R)² = 2·g·重建成本 / b
```

即

```
T* = R + √( 2·g·(pMiss·R + pOut·s) / pHit )
```

---

## 3. 代入与扫描

`R = 0.02 × 1,000,000 = 20,000`：

```
T* = 20,000 + √(2 × 5500 × 0.032 / 2e−8) = 152,665  →  15.3%
```

扫描（步长 2%）给出 **16.0%** 为最优，与闭式解一致：

| 阈值 | `T` | 周期步数 | 重建/天 | 平均上下文 | 每天成本 |
|---|---|---|---|---|---|
| 8% | 80,000 | 11 | 36.7 | 50,000 | ¥2.3733 |
| **16%** | **160,000** | **25** | **15.7** | **90,000** | **¥2.0229 ★** |
| 32% | 320,000 | 55 | 7.3 | 170,000 | ¥2.3947 |
| 48% | 480,000 | 84 | 4.8 | 250,000 | ¥2.9530 |
| 80% | 800,000 | 142 | 2.8 | 410,000 | **¥4.1703** |

**稳健区间（比最优差 ≤2%）：14% ~ 18%。**

---

## 4. 两个必须知道的耦合

### 4.1 保留得越多，阈值要抬得越高

`R` 抬高会同时抬高单次重建成本，于是最优阈值跟着抬：

| `R` | 最优阈值 |
|---|---|
| 10,000 | 12.0% |
| **20,000** | **15.3%** |
| 50,000 | 23.5% |
| 100,000 | 34.8% |
| 160,000 | 46.8% |

桌面端原有的 `retainRatio` 缺省是 **0.16**（→ R = 160,000），配 0.8 的阈值其实"自洽"；
但那是用**大量逐字上下文**换来的，代价是每次重建都要重读 16 万 token。
本文取 `retainRatio = 0.02`，把这块压下来。

### 4.2 增长越快，阈值要抬得越高

| `g` | 最优阈值 |
|---|---|
| 1,000 | 7.7% |
| 3,500 | 12.6% |
| **5,500** | **15.3%** |
| 10,000 | 19.9% |

换了模型、或者工具表大改（每步产出更多）时，用公式重估一次量级，再重跑扫描确认。

---

## 5. 🔒 安全下限：为什么不能更小

**判据一句话**：`thresholdRatio × W` 必须**明显大于固定开销 F**（系统提示词 + 工具 schema），
否则普通请求一开局就已经越过阈值 —— **每一轮都会压缩**，越压越慢越贵。

本机观测到的最小首请求约 **8.4k token**，而 `0.16 × 1,000,000 = 160,000`，留有近 **20 倍**余量。
MoonBot 那边把下限钉在 `MIN_THRESHOLD_RATIO = 0.08`，同一个道理。

> 反例（MoonBot 线上真实踩过）：阈值曾被写成 0.005 → 上下文刚到 5k 就压缩，等于每轮都压；
> 0.06 时固定开销本身就有 2.75 万 token，62.9k 的阈值被顶穿 → **114 个模型步触发 46 次摘要**。

## 6. 落地在哪

| 参数 | 落点 |
|---|---|
| `thresholdRatio` / `retainRatio` / `maxTokens` | `~/.dsh/profiles/web/cordis.patch.yml` → `id: compaction-basic` |
| 剪枝预算 | 同上 → `id: tool-result-pruner`（8192/4096/1024，与 MoonBot 出厂值一致） |

⚠️ 两处都必须写 `disabled: false` —— `dsh-web-app` 那一层把自动压缩**禁用了**，
profile 补丁是「整块替换」语义，不显式打开就一直是关的。

改完**要重启 DSH** 才生效（压缩参数是加载期配置）。

---

## 7. 怎么重算

```sh
node docs/dsh-compaction-math.mjs [窗口=1000000] [每步增长g=5500] [每天步数=400] [落点R=20000]
```

什么时候必须重算：

- **换服务商或改价** —— 命中的折扣率直接决定最优点（本文 50×）
- **换模型**（窗口 `W` 变了）
- **工具表大改**（每步增长 `g` 变了）
- 观察到的压缩频率与模型差得远

---

## 8. 已知的、本文没有覆盖的部分

- `g = 5,500 tok/步` 是由 `(未命中+输出) ÷ 步数` 反推的**量级估计**，不是逐步回归。
  桌面端目前拿不到逐请求时间序列（会话日志是 zstd 多帧拼接，`.zst` 的流式解压在 Node 里会 abort），
  所以这里用的是聚合量。要更准需要能逐条读会话日志。
- `a₀ = ¥0.002` 沿用 MoonBot 的回归截距（同一套价格结构），未在桌面端独立回归。
- 模型假设**上下文线性增长**且周期只由阈值决定；真实步长分布有抖动，这也是扫描值（16.0%）
  与闭式解（15.3%）略有差异的原因。
- **不影响结论**：最优点的位置对 `a₀` 不敏感（它与阈值无关），而 `g` 只影响阈值的高低趋势 ——
  两条独立路径（闭式解与扫描）给出 15.3% 与 16.0%，且与 MoonBot 的 0.16 撞在同一个点。
