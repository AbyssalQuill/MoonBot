# 上下文与成本的数学

本文是 MoonBot Pro 的**成本模型**：钱花在哪里、压缩阈值 0.16 是怎么算出来的、为什么"永久会话"比"按轮数换新会话"便宜，以及另外两个实测出来的优化（发字节拍钳制、MCP 压缩代理）。

本文的每一个数字都是**实测**的，来源写在旁边。要重算就跑 `qq-bridge/tools/compaction-threshold.mjs`。

---

## 0. 一句话结论

> **上下文本体几乎不花钱；花钱的是"整段重读"。**
> 所以最省钱的做法是**少压缩**，而不是把上下文压小。压缩阈值应当取在 0.16 附近（稳健区间 0.14~0.20），而不是越小越好。

这与直觉相反，也是这个阈值改了四次（`0.06 → 0.12 → 0.08 → 0.16`）之后才定下来的结论。前三次用的都是"每次请求平均花费 对 上下文大小"的**粗口径**，把两类完全不同的请求混进了同一个桶：

- **常规步**：前缀命中缓存，只按缓存价计费（很便宜）
- **重建步**：压缩 / 轮换 / 长时间空闲之后，前缀变了，**整段上下文要按未命中重读一遍**（很贵）

于是"上下文越大越贵"看着成立，实际是"**重建次数 × 上下文**"在作怪。

## 1. 计价模型

单位：¥ / 百万 token（M tok）。定义在 `qq-bridge/config.json` 的 `tokenCost` 段与 `qq-bridge/src/core/config.js:108-115`：

| 符号 | 值 | 含义 |
| --- | --- | --- |
| `pMiss` | **1 ¥/M** | 未命中输入（缓存未命中的 input token） |
| `pHit` | **0.02 ¥/M** | 缓存读（cache read） |
| `pOut` | **4 ¥/M** | 输出 |
| `peakMult` | **2** | 高峰倍率 |
| `peakHours` | `[9,10,11,14,15,16,17]` | 北京时间 **09–11 点与 14–17 点**，这几个小时整体 ×2 |

单次请求成本：

```
cost = (cacheRead·pHit + prompt·pMiss + completion·pOut) / 1e6 × peakMult
```

（实现在 `tools/compaction-threshold.mjs:26-29` 的 `costOf`；管理端口径见 `qq-bridge/src/core/token-report.js:19-25` 与 `src/pages/Learning.tsx::COST_DEFAULT`。）

> 注意：`pHit / pMiss` 差 **50 倍**。这是整个成本结构的支点——**缓存命中与未命中是两种完全不同的商品**。

## 2. 实测数据

样本：`qq-bridge/state/token-usage.jsonl`，**主聊天会话**（`private:` / `group:`）、真实用量行（排除 `est === true` 的估算行）：

```
4,659 次请求 / 11.2 天
```

（筛选口径与 `tools/compaction-threshold.mjs:41-42` 一致：旁路会话——摘要器、学习、记忆抽取——的频率与阈值无关，必须排除。）

### 2.1 按上下文大小分桶

把请求按**上下文大小（cacheRead token）**分桶，看每桶的**每次请求平均成本**：

| 上下文区间 | 占请求比例 | 平均成本/请求 | 其中"大未命中"（≥20k）占比 |
| --- | --- | --- | --- |
| 0–30k | 5.8% | **¥0.0382** | **49.8%** |
| 30–50k | 36.8% | ¥0.0105 | 10.6% |
| 50–70k | 22.2% | ¥0.0033 | 0.9% |
| 70–90k | 15.6% | ¥0.0043 | — |
| 90–120k | 13.2% | ¥0.0040 | — |
| 120–160k | 5.5% | ¥0.0051 | — |

**这张表就是全部证据。** 看第一行与第三行：

- 上下文 **0–30k** 的请求，**接近一半是大未命中** —— 那正是"刚压缩完 / 刚冷启动"的那些步，每一步都在按 1 ¥/M 重读整段
- 上下文 **50–70k** 的请求，每次只要 **¥0.0033** —— 比小上下文那桶**便宜十倍**

**大上下文本身几乎免费**；真正隔一段时间咬一口的是"压缩后第一次请求要整段重读"。

### 2.2 回归（只取 ≥50k 的常规步）

避开"刚重建完"的冷启动桶，对 `cacheRead ≥ 50,000` 的请求做线性回归：

```
cost ≈ ¥0.0020 + 0.022 ¥/M × context
```

- 斜率 **0.022 ¥/M** ≈ 缓存读价（`pHit = 0.02 ¥/M`）。也就是说"上下文每多 1M token、每次请求多花 2.2 分"，**本质上就是缓存命中价**
- 截距 **a₀ = ¥0.0020** 是每次请求的固定开销（输出、系统开销等已经吸收在这个截距里）

### 2.3 重建事件的单价与频率

`tools/compaction-threshold.mjs:66-83` 的判据：同会话内上下文**大幅回落（< 前一次 60%）** = 压缩/轮换发生了。

| 量 | 实测值 |
| --- | --- |
| 单次重建成本 | **≈ ¥0.036** |
| 频率 | ∝ 1/阈值（压得越勤，重建越多） |
| 压缩后落点（floor） `R` | **≈ 28.7k token**（脚本缺省 `28672`） |

### 2.4 缓存 TTL 的行为

按两次请求之间的时间间隔分组，看 `miss / context` 的中位数：

| 会话内间隔 | 中位 `miss / context` | 含义 |
| --- | --- | --- |
| **< 30 分钟** | **≈ 0.005** | 前缀基本完整命中，只重读千分之五 |
| **> 2 小时** | **0.84** | 前缀几乎全失效；其中 **60% 是完整的整段重读** |

**推论**：把对话"养热"比把它"压小"值钱得多。一次 2 小时的空闲，代价约等于一次重建；而多背 40k 上下文，每步只多花 ¥0.0009。

## 3. 每日成本模型

```
cost/day = steps/day × (a₀ + b · C̄) + rebuilds/day × rebuildCost
```

| 参数 | 实测值 | 说明 |
| --- | --- | --- |
| `a₀` | **¥0.0020** | 每步固定开销（来自 §2.2 回归截距） |
| `b` | **0.022 ¥/M** | 每 token 每步的边际（来自 §2.2 回归斜率） |
| `steps/day` | **≈ 416** | 4,659 次 / 11.2 天 |
| `rebuildCost` | **≈ ¥0.036** | §2.3 |
| `R` | **≈ 28.7k token** | 压缩后落点（floor） |
| `g` | **≈ 990～3,550 token/步** | 每步增长，**两个估计器给出的区间** |
| `C̄` | `(R + T)/2` | 一个压缩周期内的平均上下文（线性增长假设） |

其中 `T = thresholdRatio × W`（`W` 是模型的上下文窗口，脚本缺省按 **1,000,000 token** 算）。

### `g` 的两个估计器为什么差 3.5 倍

`tools/compaction-threshold.mjs:88` 与配置注释里出现的是同一个量、不同算法：

- 估计器 A（脚本里实际用的那个）：`g = max(500, (median(cacheRead) − R) / N₀)`，`N₀` = 周期的**中位步数**
- 估计器 B：由"压缩后落点"与"周期长度"直接推

两个估计器给出的区间是 **990 ~ 3,550 token/步**。用这个区间反推周期步数与重建频率（见下），**上端（3,550）与线上观察到的 11.2 次/天对得上**，所以缺省标定取的是接近上端的值。

## 4. 阈值扫描：最优在 0.16

把 §3 的公式对阈值比例做扫描（`tools/compaction-threshold.mjs:104`，步长 0.02）：

| `thresholdRatio` | 模型每天成本 | 备注 |
| --- | --- | --- |
| **0.08** | **¥3.34/天** | 实测同点 ¥3.49/天（偏差 **−4%**，可作标定）；重建 **15~29 次/天** |
| **0.12** | ¥2.67/天 | |
| **0.16** | **¥2.53/天** | **★ 最省（并列）· 出厂缺省值** |
| **0.18** | **¥2.53/天** | **★ 最省（并列）** |
| **0.25** | ¥2.66/天 | 比最优差约 5% |

- **稳健区间（比最优差 ≤2%）：0.14 ~ 0.20**
- 出厂值取 **0.16**（区间中部），压缩次数从 28.7 次/天降到 **11.2 次/天**
- **模型标定**：在 0.08 处模型算 ¥3.34/天、实测 ¥3.49/天，偏差 **−4%** —— 所以这套模型是可用的，不是拟合出来的故事

反推周期步数 `N = (T − R)/g`（`R = 28,700`，`W = 1,000,000`）：

| 阈值 | `T` | `T − R` | `N`（g=3,550） | `N`（g=990） | 重建次数/天（g=3,550 / g=990） |
| --- | --- | --- | --- | --- | --- |
| 0.08 | 80,000 | 51,300 | 14.5 步 | 51.8 步 | 28.7 / 8.0 |
| 0.16 | 160,000 | 131,300 | 37.0 步 | 132.6 步 | 11.2 / 3.1 |

两个 `g` 估计器给出的重建频率区间（8.0~28.7 次/天）**包住了表里记的 15~29 次/天**，并且上端 28.7 与配置注释里的数字逐字一致。这也是为什么标定取的是接近上端的 `g`。

> ⚠️ **未能完全核实的一处**：把 `a₀ = ¥0.0020`、`b = 0.022 ¥/M`、`steps/day = 416`、`C̄ = 94,336` 代回 `stepsCost = 416 × (0.0020 + 0.022e−6 × 94,336) ≈ ¥1.70/天`，加上 `11.2 × 0.036 ≈ ¥0.40/天`，我复算得到的 0.16 处总额约 **¥2.10/天**，低于表里的 **¥2.53/天**。差额（约 ¥0.43）的来源我在本轮没有定位到 —— 可能是峰谷倍率在扫描中的处理、`C̄`/`g` 的取法、或输出计价的另一处修正。
> **这不影响本文的结论**：扫描是**相对**比较（同一个模型对不同阈值求最小值），最优点位置与稳健区间不依赖绝对刻度。要拿到权威数字请在你自己的 `state/token-usage.jsonl` 上重跑 `node tools/compaction-threshold.mjs`。

### 4.1 为什么下限是 0.08（不能更小）

`qq-bridge/src/lib/dsh-compaction.js:51` 的 `MIN_THRESHOLD_RATIO = 0.08`，来自更早的四个现场：

1. 阈值曾被写成 **0.005**（窗口的 0.5%）→ 上下文刚到 ~5k 就压缩，等于每轮都压
2. 阈值 **0.06** 时，**固定开销本身就有 2.75 万 token**（system 5.36 万字符 + 78 个工具 8.11 万字符），加上历史，62.9k 的阈值被顶穿 → **114 个模型步触发 46 次摘要**，每步之间多花 15~20 秒
3. 抬到 0.12 后不再每步压缩，但上下文长期停在 ~11.7 万 token，主人实测"一句话 1 分钱" —— 于是收到 0.08
4. 按区间分桶重算（本文 §2）才发现第 3 条那次把"冷启动/压缩后重建"和"上下文大"混在了同一个桶里

判据一句话：`thresholdRatio × 模型窗口` 要**明显大于固定开销**，同时大于 `固定开销 + 保留量`，否则会"压完立刻又压"。

### 4.2 固定开销 F 的实测值

| 量 | 值 |
| --- | --- |
| `F`（系统提示词 + 工具 schema） | **≈ 28.7k ~ 33k token**（**提示词压缩工作之前**，取上下文的 p05） |
| 提示词压缩后 | system **32,963 字符** + tools **≈15.4k 字符** |

这解释了 §1 的一个推论：**`F` 直接决定阈值的下限**。如果 `thresholdRatio × W < F`，普通请求一开局就已经越过阈值 —— 每一轮都会压缩。

## 5. 闭环：最优周期与"智能推荐公式"

前四节的模型是"给定阈值算成本"。反过来问"**最优的周期长度是多少**"，就要解一个最小化问题。

设一个压缩/轮换周期的步数为 `N`：

- 周期内上下文从 `R` 线性长到 `T = R + g·N`，所以**平均**是 `C̄ = R + g·N/2`
- 每步承载成本 = `h · C̄`，其中 `h` = **每 token 每步的有效价格** = **0.022 ¥/M**（§2.2 实测）
- 周期事件本身（重建 `R` 的未命中读 + 生成摘要）单次成本 = `pMiss·R + pOut·s`
  - `s` = 摘要体量 ≈ **3,000 token**
  - 摊到每步 = `(pMiss·R + pOut·s) / N`

于是：

```
φ(N) = h·(R + g·N/2) + fixed + (pMiss·R + pOut·s)/N
```

对 `N` 求导并令其为零：

```
dφ/dN = h·g/2 − (pMiss·R + pOut·s)/N²  = 0
```

得到**最优周期**：

```
        ⎡ 2·(pMiss·R + pOut·s) ⎤
N* = √ ⎢ ───────────────────── ⎥
        ⎣        h · g         ⎦
```

### 代入实测值

先算单次事件的成本：

```
pMiss·R = 28,700 × 1      / 1e6 = ¥0.0287
pOut·s  =  3,000 × 4      / 1e6 = ¥0.0120
─────────────────────────────────────────
合计                            ≈ ¥0.0407
```

（注意它和 §2.3 直接量到的**重建单价 ¥0.036** 同量级，互为印证。）

再用 `h = 0.022 ¥/M = 2.2e−8 ¥/token`：

| `g` | `h·g` | `N*` | 对应阈值 `(R + g·N*)/W` |
| --- | --- | --- | --- |
| 3,550 | 7.81e−5 | **30.4 步** | 13.7% |
| 990 | 2.178e−5 | **57.5 步** | 8.6% |

如果直接用**实测**的重建单价 `c_rebuild = ¥0.036` 代替分解式，公式简化为：

```
N* = √( 2·c_rebuild / (h·g) )
thresholdRatio* = ( R + g·N* ) / W
```

代入即得 `N* ≈ 30.4 / 57.5 步`、`ratio* ≈ 13.7% / 8.6%`。

### 与阈值扫描的关系

闭环公式给出的推荐区间（**8.6% ~ 13.7%**）比扫描最优（**16%**）**略低**，两者不完全一致。差异来自建模假设：闭环假设上下文**线性增长**且周期只由一个参数决定；扫描用的是真实的步长分布与实测频率。

**但两者的方向完全一致**：都远高于 0.08，都落在"**阈值不该太小**"这一侧。这才是本轮重算真正的结论。

> 实践建议：以扫描值 **0.16** 为准（它已经在线上跑过）；闭环公式当作**交叉校验** —— 如果你的 `g` 明显变了（换模型、换人设、工具表大改），先用公式估个量级，再重跑扫描确认。

## 6. 轮换（新会话）的最优点

### 6.1 问题

"按轮数换新会话"（`social.autoReset.wakeThreshold`）与"永久会话"（`social.autoReset.permanent: true`）哪个便宜？

**换新会话的代价**（至少两项）：

1. **一次完整的整段前缀重建**：新会话没有缓存，`pMiss · F`
   - `F ≈ 33,000 token`（§4.2）
   - `pMiss·F = 33,000 / 1e6 × 1 =` **¥0.033**
   - `F` 取下界 28.7k 时是 **¥0.0287** —— 也就是 **≈ ¥0.028 ~ 0.033**
2. **丢失上下文记忆**：模型不知道刚才聊了什么，要多花工具往返重新查（这部分不进公式，用系数兜）

**继续用老会话的代价**：只有承载，`h · C̄` 每步。`h = 0.022 ¥/M`。

取 `C̄ = 95,000 token`：

```
h · C̄ = 95,000 × 0.022 / 1e6 = ¥0.00209 / 步
```

### 6.2 纯成本盈亏平衡点

**① 只看"多付一次重建"**

```
N · h·C̄  =  pMiss·F
N₀ = pMiss·F / (h·C̄) = 0.033 / 0.00209 ≈ 15.8 步
```

**② 再算上"轮换后上下文从 R 重新长起来"的节省**

轮换把上下文打回 `R ≈ 28,700`，每步省下 `h·(C̄ − R)`：

```
h·(C̄ − R) = (95,000 − 28,700) × 0.022 / 1e6 = ¥0.001459 / 步
N₁ = pMiss·F / (h·(C̄ − R)) = 0.033 / 0.001459 ≈ 22.6 步
```

**③ 工程口径（`F` 与 `C̄` 都用 token 直接写）**

把这套记法写成"不带单位的比例式"，就是实际在用的启发式：

```
                F
盈亏平衡步数 ≈ 4 · ─────
              b · C̄
```

（`F`、`C̄` 同为 token；`b = 0.022 ¥/M`。取 `pMiss = 1`，这个式子与 `4 × pMiss·F / (h·C̄)` 等价。）

代入 `F = 33,000`、`C̄ = 95,000`：

```
4 × 33,000 / (0.022 × 95,000) = 132,000 / 2,090 ≈ 63 步
```

**≈ 60 ~ 70 步**。因子 **4** 是给"丢失上下文"和"重新建立状态要多走的工具往返"留的经验余量，不是从公式推导出来的常数。

### 6.3 三条结论

**① 每步成本随轮换间隔的对照表**（把一次重建摊到 `N` 步上）

| 轮换间隔 `N` | 重建摊到每步 `pMiss·F/N` | 承载 `h·C̄` | 合计 | 相对"不轮换"多付 |
| --- | --- | --- | --- | --- |
| 10 步 | ¥0.00330 | ¥0.00209 | ¥0.00539 | **+158%** |
| 16 步 | ¥0.00206 | ¥0.00209 | ¥0.00415 | +99% |
| 23 步 | ¥0.00143 | ¥0.00209 | ¥0.00352 | +68% |
| 63 步 | ¥0.000524 | ¥0.00209 | ¥0.00261 | +25% |
| 417 步 | ¥0.0000791 | ¥0.00209 | ¥0.00217 | +4% |

（保守口径：这里假设轮换后的会话仍然承载同样的 `C̄`；真实情况是它从 `R` 重新长起来，所以轮换的**收益更小**、结论更强。）

**② 实测的节奏远长于盈亏平衡点。** `steps/day ≈ 416`，而"一次会话能聊多少步"是以天计的。也就是说：**按轮数频繁换会话，是在一个永远不该换的地方付重建费。**

**③ 所以：纯粹从成本讲，永久会话赢。** 配置里对应的是

```jsonc
// qq-bridge/config.json
"social": {
  "autoReset": {
    "permanent": true,      // ← 这个键
    "wakeThreshold": 10     // 保留为"压缩配置被写坏"时的兜底
  }
}
```

> ⚠️ **键名提醒**：代码里是 `social.autoReset.permanent`（`qq-bridge/src/core/config.js:296`、`qq-bridge/src/core/wake-send.js:93` 的 `rotateThresholdOf()`）。本文档集中**没有** `social.context.permanent` 这个键。
>
> `rotateThresholdOf()` 在 `permanent === true` 时返回 `Infinity`，于是所有判定（写成 `count >= threshold`）天然恒为 false —— 轮换块、busy 分支的"先别注入等收尾"、turn-hold 的"到点放行关回合"、控制台的 `[Rotate]` 收尾指令**一处不改就自动停用**。上下文治理改由 DSH 侧负责（先剪工具结果，聊天超阈值才摘要）。

### 6.4 那轮换还有什么用？

**安全阀**。三种情况下仍然应该让它换：

1. **压缩配置被写坏 / DSH 侧压缩完全不生效**：单会话会一直长下去，`wakeThreshold` 是最后一道保险
2. **换了 `agentPreset`**：preset 只在建会话时绑定（`qq-bridge/src/lib/dsh-compaction.js:293-295`），老会话要等轮换或归档重建才能拿到新提示词
3. **上下文被污染**（模型死循环、话题彻底跑偏）：`/reset` 是人工的安全阀

另外要注意"推迟注入"的**防卡死**设计（`qq-bridge/src/core/wake-send.js:70-72`）：一旦决定轮换，新消息在最多 `ROTATE_DEFER_MAX_MS = 120000`（2 分钟）内不再注入在途回合；超时后 `rotationDue()` 自动改判 `false`，消息照常注入 —— **宁可晚一点轮换，也绝不把用户的消息扣死**。

## 7. 另外两个实测出来的优化

这两条都不改计价模型，但都是**用同一份实测数据抓出来的**，且都在代码里有硬实现。

### 7.1 发字节拍钳制（`clampSendPace`）

**这是"钱之外"的一次实测量化：延迟也是成本。**

现场（线上数据，不是推测）：服务器那份 `config.json` 的 `social.send` 被调成了

```
linearPerCharMs: 650      linearCapMs: 15000
```

于是"一次回复里第 2 条气泡起 = 本条字数 × 650ms"。**17 个字 = 11.0 秒。**

DSH 会话日志里每一条 `qq_send_message` 的结果都带着这个数：

```
delays: 5237 / 8050 / 9388 / 10989 / 11753 ms
118 次发送总计执行 990 秒
```

主人感觉到的"**唤醒后要响应一段时间**"就是它。

**顺带排除了两个嫌疑**（这部分同样是实测）：

- **不是 MCP 压缩代理**：那段窗口里 `napcat_get_tool_schema` **一步都没有过**（0 次额外往返）
- **不是模型的思考**：每步首个 token 0.7~1.7 s，纯文本步 1~2 s，都是命中前缀缓存的正常值

**修法**（`qq-bridge/src/core/config.js:393` 的 `clampSendPace`）：

| 键 | 钳制区间 |
| --- | --- |
| `linearPerCharMs` | `[60, 320]` ms |
| `linearCapMs` | `[800, 6000]` ms |
| `linearMinMs` | `[0, 2000]` ms，且不得高于 `linearCapMs` |

判据是"真人聊天打字大约 **4~5 字/秒**（200~250 ms/字）"：拟人的"按字数"节奏完整保留，但绝不会退化成"发一条等十几秒"。

**为什么用钳制而不是只改配置值**：这些键**模型自己在私聊里就能改**（`core/console-server.js` 的可调项名单里有 `linearPerCharMs` / `linearCapMs`），只改文件的话下一次自调又会回来。`linearEnabled: false`（完全不延迟）不受影响，仍原样生效。

回归测试：`qq-bridge/tests/send-pace-clamp.test.js`。

### 7.2 MCP 压缩代理（开源 mcp-compressor）

工具 schema 是请求体里最大的一块，而且**每一步都重发一遍**。实测（`qq-bridge/tools/tool-schema-meter.mjs`）：约 **8.0 万字符 ≈ 2.4 万 token/步**，而一次请求的 system 只有约 5.4 万字符。

**结论很硬：少注册一个用不到的工具，比把提示词写短几个字重要两个数量级。**

#### 三个层次的压缩，别混

| 机制 | 位置 | 压的是什么 | 实测效果 |
| --- | --- | --- | --- |
| **工具裁剪档位** | `qq-bridge/src/lib/tool-tiers.js`（`social.slimTools.level`） | **注册期排除工具**——不在名单里根本不注册 | `off 100% → low 53.2% → medium 40.3% → high 29.7% → extreme 7.1%` |
| **描述压缩档** | `qq-bridge/src/lib/tool-schema-compress.js`（`social.slimTools.schemaLevel`） | 只压**描述文字**，工具与参数一个不少 | `off 89,603 字符 → medium 61,587（68.7%）→ high 27,109（30.2%）` |
| **MCP 压缩代理** | `qq-bridge/src/lib/dsh-side.js:171-296`（`social.toolCompressor`） | 把 90 个工具压成 **2 个包装工具**，工具清单塞进包装工具的描述里 | 见下 |

#### 代理的实测口径

用**我们这个真实的 90 个工具**挂上代理跑（`qq-bridge/src/lib/dsh-side.js:174-176`）：

| 代理档位 | 工具表占完整工具表的比例 |
| --- | --- |
| `low` | **38.8%** |
| `medium` | **14.0%** |
| **`high`** | **6.2%** |
| `max` | **3.6%** |

档位语义（搬的是 mcp-compressor 自己的定义，`tool-schema-compress.js:5-10`）：

| 档位 | 语义 |
| --- | --- |
| `low` | 保留描述，只做去冗余 |
| `medium` | 每条描述**只留第一句** |
| `high` | **完全不发描述**，只留工具名 + 参数名 + 类型 |
| `max` | 连工具清单都不发，改用 `get_tool_schema` / `invoke_tool` 两个包装工具 |

#### 代价：一步变两步 —— 但**实测没有变**

代理的**理论代价**是：模型遇到不熟的工具要先 `get_tool_schema` 再 `invoke_tool`，**一步变两步**。

**实测**：在一整个观察窗口里，`napcat_get_tool_schema` 的调用次数 = **0**。

也就是说，在我们这个场景里（工具名本身表意清楚：`qq_send_sticker` / `qq_send_meme` / `qq_memory_remember`…），模型**没有产生任何额外的往返**。这条既是"代理为什么默认恒开"的依据，也是 §7.1 里排除"代理慢"嫌疑的关键证据 —— 两处是同一个测量。

桥侧的必配项：代理模式下面向模型只有两个包装工具，而桥下面一整段逻辑（发送类判定、漏引号兜底、幂等账本、抽签登记、回合收尾，**49 处**）全是按**真实工具名**判断的。所以 `core/mux.js` 的 `unwrapCompressedToolName(name, rawArgs)`（`mux.js:127`）会把 `invoke_tool` 的真实目标从 `args.tool_name` 里解包出来 —— **不解包就等于全部失灵**（消息发出去了不记账、引用与收尾逻辑认不出来）。

代理的**兜底**（`dsh-side.js:179-181`、`221-247`）：压缩机没装 / 起不来时**绝不能把工具表搞没**（那等于机器人失能），所以先做一次廉价探测，探不到就直连并把原因写进日志。

> Windows 上的一个实测坑：`pip install mcp-compressor` 装出来的是 `%LOCALAPPDATA%\Programs\Python\Python3XX\Scripts\mcp-compressor.exe`，它在**当前 shell 的 PATH 里**（`where` 找得到），但 DSH 是管理器拉起的进程、继承的是另一个环境，PATH 不一定带 Python 的 Scripts 目录 —— 于是"明明装了却判成没装"、静默回退直连。所以候选路径里把 Windows 上几个常见的 Scripts 位置也列上了（`dsh-side.js:190-219`）。

### 7.3 与压缩阈值的关系：三者的钱是分开的

| 支出来源 | 量级 | 控制手段 |
| --- | --- | --- |
| 上下文承载（每步重发） | `h · C̄` = ¥0.00209/步 @ C̄=95k | 不值得为它压缩（§0 的结论） |
| 重建事件（压缩 / 轮换 / 冷启动） | ¥0.028~0.036 / 次 | `thresholdRatio`、`permanent` |
| **固定开销（系统提示词 + 工具 schema）** | **28.7k~33k token / 步，每一步都付** | **`slimTools` / `schemaLevel` / `toolCompressor`** |

第三行是**唯一"每一步都要付一次"的大头**。举例：把工具表从 100% 压到 6.2%，按 24,014 token/步 的实测基数，每步省下约 **22,500 token** —— 这个量级远超"把上下文从 120k 压到 90k"省下的每步 `h × 30k ≈ ¥0.00066`。

**所以省钱的优先顺序是**：

1. 工具表（每一步都重发，且体积最大）
2. 少压缩 / 少轮换（避免重建）
3. 保持会话"热"（避免 >2 小时空闲造成的 84% 前缀失效）
4. 提示词文案本身

## 8. 两个必须守住的硬约束

压缩配置写在 DSH home 级的 `cordis.patch.yml`（`qq-bridge/src/lib/dsh-compaction.js`）。下面的约束违反的话，**插件会拒绝加载、DSH 起不来**：

1. `compaction-basic`：`retainRatio` 必须**小于** `thresholdRatio` 解析出的阈值
2. `tool-result-pruner`：`headChars + 标记 + tailChars ≤ thresholdChars`
   - 标记是 `"\n\n[... tool result middle pruned ...]\n\n"`，与 DSH 里的 `PRUNE_MARKER` **逐字一致**

`normalizeCompaction()` 保证这两条永远成立，被夹紧时写日志说明（`dsh-compaction.js:65-90`）。相关缺省：

| 键 | 值 | 说明 |
| --- | --- | --- |
| `thresholdRatio` | **0.16** | 本文 §4 |
| `retainRatio` | 0.02 | 最近 2% 的上下文**逐字保留** |
| `toolResultMaxChars` | **8192** | 单个工具结果超过就剪成"开头 60% + 标记 + 结尾 20%" |
| `headChars` / `tailChars` | `0.6 / 0.2 × toolResultMaxChars` | 剩下 20% 留给标记 |
| `SUMMARY_MAX_TOKENS` | 4096 | 摘要请求的输出上限（DSH 缺省是 8192，这里收紧） |

`toolResultMaxChars` 从 1500 抬到 8192 的原因（`dsh-compaction.js:76-78`）：1500 太狠 —— `qq_get_prompt` 返回的整段协议、会话状态、角色卡、贴纸清单动辄好几 KB，一律被剪成"开头 900 字 + 标记 + 结尾 300 字"，模型等于只看到个零头，**越用越像"不知道工具叫什么、不知道规矩"**。

另一个真机复现的坑：**web profile 下这两行默认是 `disabled: true`**（归 host plane 所有）。即使配置写得再对，自动压缩也一次都不跑 —— 本机隔离 home 的 86 个会话日志里 `compaction/*` 事件 **0 条**；另起一个 web 实例、塞进 37k 字符的工具结果（压力 2.7 万 token，阈值才 1572），日志里依旧一条 prune 都没有；**同样的配置在 headless profile 下立刻剪枝**。补上 `disabled: false` 后立即复现成功（真机验证：37k 字符的工具结果被剪成 1239 字符，剪枝后压力降到阈值以下 → 跳过摘要、聊天记录一字未动）。所以 `buildCompactionRows()` 必须显式写 `disabled: false`（`dsh-compaction.js:112-123`）。

## 9. 怎么重算 / 重新标定

### 9.1 复算脚本

```bash
# 在线上跑（读的是桥侧的用量库）
cd /root/qq-bridge
node tools/compaction-threshold.mjs                 # 缺省 stateDir=../state，窗口 1,000,000
node tools/compaction-threshold.mjs ../state 1000000
```

脚本做的事（`tools/compaction-threshold.mjs`）：

| 步骤 | 行 | 输出 |
| --- | --- | --- |
| 读 `state/token-usage.jsonl`，筛主聊天 + 真实行 | 31-46 | 样本数、跨度天数、steps/day、实测 ¥/天 |
| ① 对 ≥50k 做回归 | 56-64 | `a₀` 与 `b`（边际 ¥/M） |
| ② 量重建单价与周期 | 66-90 | 重建次数/天、单次成本、`R`、`N₀`、`g` |
| ③ 扫阈值 | 92-121 | 每个比例对应的 ¥/天、周期步数、平均上下文 |
| 标定 | 106-124 | 模型在同一点 vs 实测的偏差（越接近 0 越可信） |

脚本末尾会打印改法：`qq-bridge/config.json` 的 `dshCompaction.thresholdRatio`（管理端「Core 设置」也能改），桥热加载后**自动重写 DSH 的 `cordis.patch.yml`，不用重启**。

轮换成本的单独量化脚本：`node tools/token-rotation-cost.mjs` —— 按 session 统计**每个会话第一次调用**里的全价新输入（缓存必须从零重建），直接给出"轮换重建占全价新输入的比例"。

### 9.2 什么时候必须重新标定

| 触发条件 | 为什么 |
| --- | --- |
| 改单价（`config.json` 的 `tokenCost`） | `pHit` / `pMiss` / `pOut` / 峰谷倍率直接进 `costOf` |
| 换模型 / 换服务商 | 缓存 TTL 与命中行为不同（§2.4），`g` 也会变 |
| 工具表大改（换档位、加/删工具） | 固定开销 `F` 变了 → 阈值下限跟着变 |
| 提示词大改（人设、`prompt.styleLine`、preset） | `F` 与每步增长 `g` 都会动 |
| 观察到"每步都压缩" | 说明 `thresholdRatio × W` 已经被 `F` 顶穿 |

### 9.3 已知的、本文没有覆盖的部分

- §4 的绝对金额与本文参数**没有完全对上**（差约 ¥0.43/天），已在 §4 明确标注；结论用的是相对比较，不受影响。
- `g` 的两个估计器差 3.5 倍，本文按"上端与线上 11.2 次/天一致"选了接近上端的标定；**没有独立验证哪个估计器更接近真值**。
- 峰谷倍率在扫描公式里的具体处理方式（是逐小时判定还是整体乘一个平均系数）我**没有在 `tools/compaction-threshold.mjs` 里逐行追**。`costOf`（`compaction-threshold.mjs:26-29`）是**逐请求**按北京时间小时判定倍率的；但扫描用的 `stepsCost` 与 `rebuildCost` 是否已经吸收了倍率的平均效应，需要重跑脚本看输出对齐。
- §7.1 的 990 秒 / 118 次发送来自现场日志与 `qq-bridge/tests/send-pace-clamp.test.js` 的记录，我**没有在本地复现**。
